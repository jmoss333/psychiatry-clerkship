# Workplace-Assessment Pack: MS3 Psychiatry Clerkship

**DRAFT for Josh's edit.** Work package WP-3, decision D5: the instruments live here, in
non-shipped `13_Faculty_Resources/Assessment/`, with an optional printable export. Nothing in
this folder ships to the MS3 or resident site. Josh's approval of the pull request that adds
this pack is its sign-off; it has no attestation row and causes no page drift.

## Purpose

The library teaches the clerkship well but, before this pack, assessed almost none of it in the
workplace. The 2026-09-24 Curriculum Architecture Review found no stated clerkship objectives, no
required-encounter list, no direct observation, no narrative assessment, and only an aspirational
midpoint check-in, and it found Core EPAs 5, 8, 9 and 13 never assessed. This pack supplies the
objectives, the list, the observation cards, the midpoint form, and the preceptor guide that
close those gaps. The instruments are formative records that feed the school's official
evaluation; none of them is itself a grade.

## LCME elements and the instruments that address them

Element titles are from the LCME *Functions and Structure of a Medical School*, 2026–27
(standards effective July 1, 2026), read at
<https://lcme.org/wp-content/uploads/2025/10/2026-27-Functions-and-Structure_2025-05-21.docx>.
The link in the handoff document has moved to that address. The eight elements below are
unchanged in the 2027–28 edition apart from the subject of 8.7.

| Element | Title | What this pack supplies | Limit |
|---|---|---|---|
| 6.1 | Program and Learning Objectives | `clerkship_objectives.md`: one list, known to everyone who teaches or assesses, cited by every card | Students see the objectives through the midpoint form now, and on topic pages once WP-13 lands |
| 6.2 | Required Clinical Experiences | `required_encounters.md`: patient types and conditions, settings, and proposed minimum responsibility | Responsibility levels and settings await Josh's confirmation |
| 8.6 | Monitoring of Completion of Required Clinical Experiences | The list the school's system tracks; students report progress at the midpoint | The monitoring system is the school's, not the library's |
| 8.7 | Comparability of Education/Assessment | A simulated alternative for every required encounter; the same cards at every site | Three alternatives are still planned (capacity and de-escalation simulations, WP-11; child cases, WP-9) |
| 9.4 | Assessment System | Direct observation of core clinical skills: DO-1 to DO-4 and the Sim-to-Ward card | The school's assessment system decides how the cards are weighted |
| 9.5 | Narrative Assessment | A narrative box on every DO card and in the midpoint form | Faculty write the final narrative in the school's system |
| 9.7 | Formative Assessment and Feedback | `mid_clerkship_feedback.md` at the end of Week 3 | The form is formative; it records no grade |
| 9.8 | Fair and Timely Summative Assessment | Nothing | Out of the library's scope |

**EPA 13 is event-dependent.** A post-event debrief happens only when an event does, so many
students will have no DO-4 variant D rating. The planned remedy is a student version of the
resident site's Post-Event Learning Huddle (review §6, Tier 2). It is not built here because it
would be a new learner-facing page, which needs full registration (manifest, nav, ledger row,
topic metadata) and so falls outside decision D5, which placed this pack in non-shipped faculty
resources.

## The rating scale

Every card that records a rating uses the same four levels, in the pack's own words: **needs
direct supervision / needs prompting / needs occasional checking / ready for indirect
supervision**. Each rates what the student needed from the observer for one task on one day.
Level 4 never changes what an MS3 may do unsupervised.

These instruments are original. They do not reproduce the ABIM mini-CEX, the O-SCORE or Ottawa
anchor wording, or any other published form. If the clerkship wants a published scale instead,
its rights status must first be recorded in `instrument_rights.json` through a governance pull
request. The OSCE station set (`osce.md`) has its own four-level entrustment anchors for station
scoring; the two scales are separate for now (see the open decisions below).

## How to print

```bash
python3 13_Faculty_Resources/_automation/build_assessment_pdf.py
```

This renders all ten files, in a fixed order, into one print-ready HTML file at
`output/assessment-pack/assessment-pack.html`. If a headless Chrome or Chromium is installed, it
also writes `output/assessment-pack/assessment-pack.pdf`; otherwise open the HTML and print it to
PDF from the browser. The output folder is ignored by git. The script is a developer tool: it is
not part of CI, `bin/verify.sh`, or either site build.

## Where completed forms go

To **[your school's evaluation system]**. Completed cards are paper or entries in that system.

## What this repository never stores

**No learner data.** No completed card, rating, narrative, student name, or score is ever
committed here or entered into the library, and no card carries patient identifiers (patient
initials: not recorded; encounter type only). The library's learning tools keep a student's
practice history in that student's browser; they do not send it to faculty.

## Maintenance

- **Objective ids are permanent.** Never renumber; retire an objective by marking it retired and
  add new ones at the end. WP-13 topic pages will cite these ids.
- `tests/assessment-pack.test.mjs` holds the pack together: all ten files exist; every DO card has
  an EPA line and cites objectives; no file carries a patient-identifier token; every objective
  is assessed somewhere and no cited id is undefined; the Foundational Competency ids are real;
  every required encounter names a simulated alternative; DO-3 matches the five `oral.html`
  self-check items; and the encounter card's crosswalk matches the Interview Room checklist.
- The `curriculum.json` week 3 `practice` entry that names the midpoint meeting arrives with
  WP-4, which adds the `practice` field; the preceptor guide's weekly table will then be
  generated from it.
