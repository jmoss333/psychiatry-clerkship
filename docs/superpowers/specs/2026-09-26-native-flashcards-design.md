# Native flashcards in Daily Review — design

**Status:** design direction approved in conversation 2026-09-26; written spec for owner review before an implementation plan.
**Date:** 2026-09-26 · **Owner:** Joshua Moss, MD · **Baseline:** local `origin/main` at `712d409`.

## 1. Intended result and current evidence

Learners should be able to study the library's reviewed concept cards on the MS3 and resident sites: see a specific prompt, recall an answer, reveal the source wording, grade their recall, and return when the card is due. The site should make the relationship between a card, its reading, and its next review clear. The existing Anki downloads remain available for learners who prefer Anki. Progress stays in each product; the site does not imply that it syncs schedules with Anki.

The checked-in combined Anki package currently contains **310 notes and 326 rendered cards**: 168 question-bank cards and 158 concept cards. It has no media. This is an observed baseline, not a fixed release count. The package and both public downloads matched byte for byte when inspected on 2026-09-26. The checked-in README has stale counts. The present Concepts exporter selects pages by an `attested by` text match, aligns curated blanks to pearl *positions*, and can fall back to vague prompts. An ethics page has eight pearls but seven mapped rows; five published cards consequently ask only “Recall the key point:”. Twenty-one summary cards ask only “In one line?”. A separate question-bank audit found that the correct answer is uniquely the longest option in 133 of 144 attested items. Twenty-four second-tier cards omit evidence and source-link fields, and the question-bank backs repeat the options before marking the answer. These are card-quality findings, not a clinical-content approval or an objective score of learner knowledge.

Daily Review already has recall/reveal/self-grading, browser-local `cw_srs_v1` scheduling, a session receipt, and timed blocks. Practice Questions already serves the question-bank material. The first release extends Daily Review with **Concepts** and links learners to Practice Questions for vignettes; it does not create a second scheduler or duplicate the question-bank UI.

## 2. Decision and boundaries

Use one tracked **candidate concept catalog** as the editorial map. It names exact source excerpts and answer targets but carries no live faculty-review status. The build validates it against the canonical pages, then projects a **released card feed** from the effective ledger applied for that build. That same released set supplies the site and the Concepts portion of the Anki packages. Each rendered card has one stable editorial ID, one prompt, one source-exact reveal, a working page link, and a source revision. Daily Review consumes the feed using its existing recall kind and SRS store.

The first release includes the concept cards eligible under the current effective review ledger, specific source-exact prompts, a temporary **This week** filter for new cards, due cards from every studied week, and a compact visual cue showing the prompt → source → next review relationship. The cue is text and CSS, with no added clinical assertion. Anki remains an optional download. The 168 question-bank cards are audited as a separate quality lane; their clinical wording and answer options are not rewritten automatically.

Out of scope: schedule synchronization with Anki, AI-generated clinical wording, learner-authored cards, new analytics events, a standalone flashcard tool, and clinical diagrams in the first release. Adobe is optional for a later faculty-authored diagram; the first release needs no raster asset. Any later visual card needs a source link, a reviewed explanation, alt text, and a text-equivalent prompt.

## 3. Card authority and data flow

```text
canonical page + tracked candidate card catalog
                    │ exact excerpt and target validation
                    ▼
       effective review ledger after overlay
                    │ release projection
                    ▼
      versioned released-card feed
          │                    │
          ▼                    ▼
   /tools/concepts.json    Concepts Anki package
          │                    │
          ▼                    ▼
   Daily Review queue     optional download
          │
          ▼
     cw_srs_v1 schedule
```

The tracked candidate catalog replaces `pearl_cards.json`'s index-aligned arrays. Every record names a permanent ID, the canonical source path, the kind (`summary` or `pearl`), the exact source sentence/bullet it selects, and one or more exact answer targets. A target is identified separately when one pearl makes multiple cloze cards. A source move or bullet reorder does not change IDs. The generator structurally extracts the summary and pearls, normalizes only inline formatting, and checks that each selected excerpt occurs **exactly once in its source section**. Each target must occur **exactly once in that excerpt**, must not overlap another target, and must be nonempty. Missing, duplicate, overlapping, or orphaned selections fail the build with the source path and ID; no generic front is emitted. An author-bolded term is not an implicit fallback. A summary becomes a source-exact occlusion question rather than “In one line?”. The catalog stores plain text plus explicit target spans; both site and Anki renderers escape it and hide the same span. Each eligible source summary and pearl is either mapped or explicitly excluded with a reason reviewed by faculty, so a growing page cannot silently shrink the deck.

Eligibility is computed from `surface_governance.load_effective_ledger()` for the **current source revision**, after any signed ledger overlay, not an `attested by` string or a raw historical review row. Only pages in the derived `shipped_pages.json` universe and effectively reviewed for the audience can contribute released cards. The initial release uses the intersection of reviewed concept sources shipped to **both** sites, allowing the same Anki package to match both. If a later page is eligible on only one site, the build names that difference and stops until the owner either approves its exclusion or designs audience-specific packages; it does not silently shrink a deck or serve mismatched downloads. A pending or drifted page withholds its cards on both sites and from newly built Anki packages. The release report records examined source *paths and statuses*, withheld IDs with reasons, and a deterministic digest of rendered cards; the tracked candidate does not copy the review ledger or the review tool's own attestation row. Empty output, partial input, or an unexamined eligible page fails validation rather than quietly looking like a small deck. The tracked candidate is an explicit teaching dependency of `review.html`, so changing a prompt or tested target makes the tool's attestation input drift and requires faculty review of its rendered faces before learner readiness is claimed. A new sign-off can change release membership without changing that attested candidate blob.

The map is editorial selection, not a license to add new clinical prose. A factual change belongs in the canonical page and its evidence annotations; a faculty reviewer then checks the exact rendered prompt and reveal. Existing title/summary/pearl boundaries remain source structure, but release eligibility is the effective ledger. No card is released solely because its old Anki package exists.

## 4. Identity, revision, and Anki migration

Each reviewable cloze has a permanent editorial ID such as `ethics-capacity:1`, independent of display order and wording. `:1` and `:2` are separate schedule items when one pearl hides two targets. The SRS key includes the content revision, for example `CONCEPT#ethics-capacity:1@2`; the shell recognizes the `CONCEPT#` prefix. The map retains the editorial ID across harmless page movement or formatting changes. A tested fact, answer target, or answer changes increments `contentRevision`, giving that card a new schedule key while retaining the older key as local history. A copy-only change may retain the schedule only through an explicit reviewed migration entry. Withdrawn cards are excluded from queues, due counts, and export; their local history is retained for possible audit but never shown as due. No unrelated `cw_srs_v1` entries are reset.

The existing Anki exporter uses a text-derived note GUID and a position-derived UID. Migration must first inventory the published note GUIDs and rendered cloze ordinals, then write an explicit **old note GUID + cloze ordinal → editorial card ID** crosswalk. Unchanged **Anki notes** keep their note GUIDs so an update does not duplicate them. A changed tested answer gets a new Anki note identity unless the owner explicitly approves an update migration. If one target changes in a multi-cloze note, its unchanged sibling may also receive the new note identity; the package diff calls this out. Site SRS items remain independent. Changed or withdrawn cards are reported by the package comparison; the owner reviews that report before a replacement package is published. A card count match alone is insufficient: validation compares stable IDs, normalized front/back content, cloze ordinals, source links, and release status. The combined package's question-bank portion is checked separately against its existing source.

## 5. Learner flow and visual treatment

**Entry.** The current **Daily Review** item stays in both sites' Practice and Exam Prep navigation. Its dashboard adds **Concepts** and shows available, due, and new concept counts. **Practice Questions** remains the path for vignette/choice cards. A small label says “Progress saved in this browser; Anki reviews are separate.”

**Study.** A card shows its topic and a precise occluded sentence. Before reveal, the answer is not present in accessible text or the DOM. Reveal presents the complete source sentence, a link to its source page, and (where the source makes a paper-specific claim) its evidence/source link. The learner grades Again, Hard, Good, or Easy using the existing scheduler. After grading, a simple visual line connects **this concept → its source → next due date**; this is a navigation and timing aid, not new teaching content. The session receipt distinguishes objectively scored choice answers from **self-rated recall**. The existing “Retention” percentage is removed: its historical `correct/seen` fields already mix choice answers with self-rated recall and cannot be split retrospectively. The fields remain readable for backward compatibility, while new additive counters separately report **Choice answers correct** and **Recall marked Good/Easy**, labeled “since this update.” No historical percentage is recast as objective accuracy.

**Week.** **This week** uses the Front Door's projected `FD_INDEX.weeks` and the actual active `state.week`, including a validated curator edition. It limits **new** Concepts to sources assigned to that week. The default is **All concepts**, so every released card, including pages with no weekly Path assignment, is reachable in an ordinary session. The filter shows how many new cards it excludes and names the unassigned group as **Other library topics**. Already studied Concepts from any week remain due, so the Today due badge and session agree. Switching between **This week** and **All concepts** does not change the Path or save filter state. When the tool is opened directly and has no trusted Path context, it offers All only. A same-origin, typed iframe request/reply carries the projected week references; the receiver validates origin, sender, and payload. It does not rely on `state.viewWeek`, which is the week being browsed. Timed `?block=1&limit=N` sessions ignore the new-card week filter and keep their present limit and receipt behavior.

All actions work with keyboard, touch, screen reader, reduced motion, and narrow viewports. Shortcuts do nothing while focus is in a button, link, input, or filter. Reveal announces the answer once; grading announces the next card or completed session. There is no flip animation required to understand content. Anki links and source links have descriptive names.

## 6. Site integration, failure behavior, and offline use

The tracked candidate catalog lives in `site_build/` and is validated against the current source pages. After the optional ledger overlay, both builders generate the released feed at `/tools/concepts.json` **before they emit `sw.js`**; this keeps the route in the service worker's precache and inside static QA. `teaching_dependencies.discover` gets one explicit generated-asset rule for this route: at source-list time it records the tracked candidate as `review.html`'s `extraSources` (the same file the faculty console hashes); at `--check-build` time it regenerates the release feed from that candidate and the effective ledger and compares the exact built bytes. It does not require the projected feed to be a tracked source file or hash `reviewed.json` wholesale into the tool's own attestation. The feed has a schema version, card list, eligibility digest, and examined-source-set digest. Its expected digest is embedded in the built `review.html` and shell; the browser checks the fetched bytes against that expectation, as well as schema and IDs, before offering Concepts or counting them due. A failed, stale, or invalid fetch shows **Concept cards unavailable** with a retry action; it never silently omits Concepts while reporting a complete deck. Other Daily Review sources retain their existing behavior, with the Concepts error visible beside them. The Front Door offline route allowlist and readiness probe must include `/tools/concepts.json` whenever Daily Review is in the selected offline pack; a precache entry alone cannot establish readiness. Offline tests verify the actual cache entry on both sites. `.apkg` downloads remain online downloads.

The shell's `srsBucket` recognizes `CONCEPT#` as Daily Review. At startup it loads and verifies the released feed asynchronously, keeping the Concepts count in **checking**, **ready**, or **unavailable** state. Its due breakdown filters versioned `CONCEPT#` keys through the feed's released-ID set; withheld or withdrawn cards cannot inflate Today. If the feed is unavailable, Today says Concepts could not be checked instead of reporting a falsely complete due count. Daily Review and the shell use the same pure eligibility rule over that set, and timed blocks use it too. The new asset receives deterministic cache-busting and freshness treatment, including an expected digest embedded at build time.

The current `build_anki.sh` is intentionally fail-soft and stages committed packages after the site's existing QA step. Dynamic ledger sign-offs make a committed package stale when release membership changes. The feature therefore pins `genanki` as a build dependency and regenerates the Concepts and combined packages from the **same post-overlay released feed** used by the site. A separate **hard freshness check** runs after staging and before either build exits successfully. It reads the staged package, compares its rendered Concepts cards with the built feed, and checks that no withheld card remains. If regeneration is unavailable, a committed package may still be used **only if** it passes this semantic comparison; otherwise the build fails rather than offering stale teaching. The check covers both MS3 and resident outputs and the combined package; a missing or unreadable package is a failure. This makes package generation a required release capability for newly signed cards, while preserving an exact-match fallback for unchanged membership.

## 7. Quality review and release sequence

1. **Inventory and repair.** Snapshot existing Anki GUIDs and rendered cards, replace positional pearl mapping, account for every current summary/pearl/cloze, and remove generic prompts. Update the deck README from measured output. Compare the pre- and post-change rendered-card list; faculty reviews any changed teaching face.
2. **Create the catalog.** Validate exact source selections, effective review state, stable IDs, revisions, audience, and source links. Generate both site feeds and Anki Concepts from it. Fail closed on partial coverage and mismatched artifacts.
3. **Connect Daily Review.** Add Concepts to recall sessions, active-week new-card selection, Today/blocks parity, accessible visual treatment, visible fetch errors, and honest self-rating labels. Do not migrate or clear other SRS cards.
4. **Review before release.** Show the owner an exact old/new rendered-card diff and an MS3/resident browser preview. Faculty approval of clinical wording and tool attestation remain separate from passing code checks. Publish only after the card faces, package diff, site builds, and deployment state have each been verified.

The question-bank audit is reported with exact item IDs and option lengths, missing evidence/source links, and a before/after template preview for faculty review. Correct-answer length is a cue risk, not proof an item is medically wrong. Faculty decides whether to rewrite options or add clinical evidence. A separate nonclinical template change can remove the repeated options from the back after checking that the correct answer and feedback remain clear. The first Concepts release does not wait for all 144 items to be rewritten, and its dashboard does not claim a mastery score from those items.

## 8. Acceptance evidence

- A test adds, removes, and reorders a pearl: exact mapping either preserves the intended IDs or fails with a named mismatch; it never emits “Recall the key point:” or silently drops a target.
- A changed source loses effective reviewed status: both site feeds and staged Anki packages withhold the cards, and the build reports the withheld IDs. A controlled fixture proves this without depending on today's live review count. A second fixture adds a valid signed ledger review after checkout and proves the new card appears in both artifacts without editing the tracked candidate.
- Every released ID is unique and reviewable once; multi-target pearls yield one schedule item per rendered cloze. A changed answer resets only that card's schedule; a withdrawn card disappears from queue and due count without deleting unrelated history.
- Real `CONCEPT#` IDs appear in Daily Review and Today's Daily due bucket. Every released ID is reachable in the default All session, including sources outside the weekly Path. Due cards remain due when **This week** changes; active and curator-edition week assignments affect new cards; a direct tool visit selects All; timed blocks keep their existing limit and receipt.
- Missing, stale, invalid, or offline-unavailable Concepts data displays a clear error and never a success count over a smaller set. Offline readiness tests load the feed on both builds. A fixture with older mixed SRS stats never displays them as an objective retention rate; new choice and recall counters start separately without inventing historical breakdowns.
- A package with one altered, missing, extra, or withheld rendered Concept card fails the hard artifact check even when the package's note count matches. Both site builds and the combined download pass only with semantic parity.
- Browser checks cover a 390 px viewport, keyboard/focus, screen-reader names and announcements, reduced motion, reveal privacy, source navigation, and clear self-rating labels. `review-recall`, SRS counter, block, Front Door, governance, build, and offline tests cover the same contracts with deterministic fixtures.

## 9. Later visual idea

A faculty-authored **decision pivot** card could show two otherwise identical synthetic cases side by side and reveal the one detail that changes the next step. It would link each answer to its approved source and include a text equivalent. This is a separate design and review step after the source-exact Concepts release; it does not turn the current deck into new clinical advice automatically.
